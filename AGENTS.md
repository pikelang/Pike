# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the C runtime, compiler, parser, and core `testsuite.in`.
- `src/modules/` and `src/post_modules/` contain native modules; `lib/modules/` contains Pike modules. Compatibility libraries live under `lib/7.8/` and `lib/8.0/`.
- `bin/` holds build generators, the installer, and test utilities; `tools/` contains developer utilities.
- `refdoc/` contains reference documentation and images; `man/` contains manual pages; `packaging/` contains platform packaging assets.
- `build/` holds generated build trees. Start with `README-GIT` for build details.

## Build, Test, and Development Commands

Git builds require an installed Pike, a C compiler, Autoconf, Bison, and GNU m4; native modules need additional libraries.

- `make`: configure and build from the repository root, keeping build products outside `src/`.
- `make CONFIGUREARGS="--with-debug"`: enable runtime checks and debugging symbols.
- `make depend`: refresh source dependency information.
- `bin/pike script.pike`: run a script using the built interpreter.
- `make just_verify`: generate and run tests with the build-tree interpreter.
- `make verify`: perform a test installation and run its tests.
- `make documentation`: generate reference documentation.

## Coding Style & Naming Conventions

Follow nearby C/Pike code: generally two-space indentation, existing brace placement, and descriptive names. Preserve existing file encodings and avoid unrelated formatting changes. Runtime functions commonly use `snake_case`; Pike module and class names commonly use `CamelCase`.

When the indentation step differs from two spaces, add a `c-basic-offset` header, for example `/* -*- mode: C; c-basic-offset: 4; -*- */`. A tab always advances to the next eight-column stop, independently of the indentation step.

Aim to keep lines within 80 characters where practical.

Edit generator inputs such as `.cmod`, `language.yacc`, and `treeopt.in`; regenerate their outputs through the build rather than committing generated C or headers. Use existing AutoDoc conventions for public APIs. Run `git diff --check` before submitting.

## Testing Guidelines

Tests use the `test_pike` runner and macros such as `test_any`, `test_equal`, and `test_compile_error` in `testsuite.in` files. Add regressions to the core or affected module suite. Test files are generated by `bin/mktestsuite`; retain fixture locations when running individual suites.

Exercise boundary cases and report commands, skipped tests, and baseline failures. For performance changes, compare equivalent builds and repeat measurements.

## Commit & Pull Request Guidelines

Use the history's subsystem-prefixed subjects, for example `Compiler [Typechecker]: Cache object and program type binops.` Keep commits focused. Describe behavior, link relevant issues, and include validation results; attach screenshots for UI changes. Update `CHANGES` for significant user-visible changes.

When staging, include only requested changes. Save requested draft commit messages in the worktree's `MERGE_MSG` path, obtained with `git rev-parse --git-path MERGE_MSG`; do not create `MERGE_HEAD` or commit without instruction.
